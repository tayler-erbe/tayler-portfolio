The Town Behind
the Characters

Agent Town is the 3D town on my desktop where every one of my AI agents has a character and a building. It looks like a game, but it is an operations console: every light, walk and animation comes from a real job, model server or file. This page is the system design of the town itself — where its data comes from, how one Python server turns that into a single snapshot, how a button press reaches the job queue, the decisions behind it, and which claims are measured and which are not.

01 / The System Map

A projection, not a second system

The town owns almost nothing. The job queue, the agents' charters, my to-do list, the money ledger, the security scans and the model servers already existed before there was a town. The server reads them, builds one snapshot of the whole world, and the browser draws that snapshot. Read the top row left to right for the data path. The one way back is the warm line: a command I confirm is written into the job queue, under the queue's own lock, and the queue’s scheduler stays the only thing that runs work.

PlaceWhat happens there
Sources of truthFiles and services that existed before the town: the job queue and its per-job state files, agent charters, to-dos, the ventures list, the money ledger, security scan folders and the model servers. The town reads them; it writes only to the queue, and only through the queue’s own lock.
Town serverOne Python process using only the standard library. It builds the world snapshot, ranks what needs me, keeps the event feed and handles commands. It listens on this machine and its private tailnet address only, never on every interface.
PagesThe 3D town is the front door. The Desk, Talk, the logs, the café and the older 2D city are separate pages on the same server, reading the same snapshot.
ModelsLocal Qwen models on vLLM and Ollama, ComfyUI for video, and Claude through the job queue’s lane. Only one ~30B model fits on the GPU at a time, so the town shows a stopped server as offline, not broken.
Scheduled workersThe queue tick, the Overseer, Recon, the Income Scout and the Foreman run on their own schedules and write into the sources. The town only shows what they did.
02 / The Town’s Rhythm

Five seconds to one week

Nothing in the town is on a timer of its own invention. Each rhythm below belongs to the system it shows, and the town just keeps up with it.

1
At logon · the server starts
A scheduled task starts the town server when I log in. Nobody restarts it by hand; tests run on a spare port.
2
Every 5 seconds · the browser asks what changed
The page asks for the world with the number of the last event it saw, gets back only the newer events, and animates them. One request at a time, with a timeout; if the server stops answering, the town says “disconnected” and keeps the last picture.
3
Every 10 seconds · the slow checks
A background refresher probes the model servers and the GPU, so a page request never waits on a slow health check.
4
Every 15 minutes · the queue ticks
The job queue’s scheduler starts whatever is allowed to start, and ticks again after each job. When I press Run now, the town asks it to tick early; it never runs the job itself.
5
Every hour · the Overseer’s round
It visits every agent and gives a thumbs up or a flag, from failed runs, stuck runs, missed schedules and offline runtimes, and asks a local model whether the newest run did its job. It checks; it never restarts or deletes anything.
6
Every 6 hours · Recon
Public news, income and job feeds are fetched (public feeds and official APIs only, no logins, no scraping), stored as untrusted text and summarised for the town’s newsroom.
7
Every week · the Income Scout
A queued job writes a report of possible income streams. Its finds wait in Needs Me for my yes or no.
8
During GPU work · the town steps aside
When a protected GPU window opens for model work, the town’s model polling is stopped for the whole window and started again only after the window is verified closed.
03 / Follow One Command

From a tap to a walking character

Ask
On my phone I tap an agent who is sleeping until next week and choose Run now.
Preview
The server answers with what will happen, which gate it will set aside, what it costs and whether it needs confirming. Nothing has changed yet.
Sign-in
The confirm request must come from this machine, or from a tailnet device whose login is mine. Anything else is refused with the reason.
Confirm
The confirmed request carries a fresh key. If the same key arrives again within 24 hours (a double tap, a retry), the stored answer comes back and no second job is made.
Write
Under the queue’s lock, one date gate on one queued job is set aside, and the original is kept so it can be put back. Approval flags, dependencies and usage limits are never overridden.
Run
The queue ticks early and its scheduler starts the job in its lane, under the same launch budget as any other job.
Shown
The next snapshot sees the job running, the event diff gives it a number, and within five seconds the agent’s character shows it at work. When the job ends, its finish or failure reaches the feed the same way.
Kept
Who did what, from which device, is in the actor log; the finished job goes into the Done log, which is never edited or pruned.
04 / How Each Part Works

The work behind each box

PROJECTIONFiles and probes in, one snapshot out
build_world is a pure function: files and a dictionary of probe results go in, one world comes out — twelve districts, their buildings, about thirty agents, the models, the GPU, money, alerts and what needs me. It re-reads only files whose modification time changed, so a warm request takes 50 to 100 ms over roughly 700 jobs and 1,400 state files.
STATE MODELOne visible state, decided in a fixed order
Each agent carries plain fields (availability, runtime, run state, attention, next run). One function turns them into exactly one visible state: blocked, waiting on me, working, queued, offline, paused, scheduled soon, sleeping or idle, in that order of precedence. “Sleeping” only ever means a future run is scheduled; a server that does not answer is offline, never asleep or done. Every pair of states is tested.
COMMANDSPreview, confirm, and only through the queue
Run now, assign a task, status check, prioritise, pause, resume, cancel, pause all and propose. Each has a preview that changes nothing; anything that sets aside a gate, spends Claude usage, pauses or cancels needs an explicit confirm. Running jobs are never touched. Propose turns free text into a structured proposal on a local model and never executes it.
NEEDS MERanked by how much work each answer unblocks
Everything waiting on me — security alerts, blocked agents, approvals, scout finds — is in one list. Decisions are scored by the queued jobs they hold up, with extra weight for held GPU work and for how long they have waited, and the calculation is shown on the card. The dependency graph is rebuilt from the queue on every snapshot, never stored.
MONEYUntracked is not zero
Money lives in an append-only ledger. Entries need evidence and stay pending until I mark them verified; refunds and reversals are entries too, and duplicates are refused. Totals count verified money only. A venture with no entries says “no revenue recorded yet”, not $0, and estimated costs appear only when I configure the rates, labelled as estimates.
THE TOWNThree.js, no build step
The 3D town is plain JavaScript modules and Three.js, served from the same machine, so it loads over the tailnet without a CDN. Buildings were assembled by Blender scripts, characters generated from concept art with Hunyuan3D and cleaned up in Blender. Animations come only from real events: a job finishing, a model going down, a verified sale. The older 2D city is Canvas 2D with pixel art drawn in code.

CONVERSATIONSTalk, board rooms, the café
I can chat with any agent on a local model or Claude, or put several in a board room. Claude speakers get read-only tools; every turn is saved, and the Chat log keeps current and archived conversations for all time. The café DJ can only propose changes to its notes on my taste; nothing is saved until I press Save.
WATCHERSChecks that report, never act
The Overseer rates every agent up, waiting, watch or down. Recon treats everything it fetches as untrusted text that is stored and shown, never executed or obeyed. The Foreman picks one next task for a sleeping department from that department’s own open list, checked by number so it cannot invent work; anything touching publishing, money, deleting or the live site waits for my approval.
The agents and their gates →
SAFETYSmall surface, nothing secret
No passwords are stored and the town holds no API keys. Every action needs a same-origin header, this machine’s host name and a known actor. Static files are served from an allow-list; files shown in the browser come only from allow-listed folders, and secrets are never printed.
05 / Design Decisions

The choices that shaped the town

DecisionWhyWhat it costs
The town is a projectionOne source of truth per fact; the town can be restarted or rebuilt without losing anythingIt can only show what some file or service records
The job queue is the only schedulerWork never runs twice or around a gate because the dashboard askedRun now can only move a date, not skip an approval
Standard-library server, no frameworkNothing to install or build; it loads over the tailnet when the internet does notRouting, caching and auth are written by hand
Polling with an event numberSimple and robust; a missed poll costs nothingUp to five seconds of delay; history is not replayed after a restart
Tailnet identity instead of passwordsPhone and laptop work without storing a password anywhereDepends on Tailscale being installed and signed in
A deterministic visible stateThe same facts always give the same picture, and it can be testedNuance is folded into nine states
Advancement from milestones, not job countsA busy agent is not the same as a useful one; security and research earn recognition without revenueThe town grows slowly
New pages behind a flagThe old page stays until the new one is trustedSeveral pages to keep working at once
06 / What Is Proven

Measured, live, built, not built

A town full of moving characters is easy to over-read. Each claim on this page falls into one of these categories.

CategoryWhat it covers
MeasuredThe automated suite: 377 passed, 10 skipped, 0 failed (19 and 26 Oct 2026). Warm snapshot requests of 50 to 100 ms over about 700 jobs and 1,400 state files (15 Oct 2026). Layout checks in headless Chromium from 390 to 1,440 px wide for the 2D city.
LiveThe server, the 3D town, the Desk, Talk, the logs and the café on my desktop and over the tailnet; the hourly Overseer, 6-hourly Recon and weekly Income Scout.
Built, limitedAutonomy preferences and decision records are journal entries, marked not enforced. Park play is opt-in and cosmetic: it never changes an agent’s work.
Not builtReal cross-agent meetings, enforced autonomy levels, music streaming, and a full terrain and water replacement.
Not measuredTime saved, Claude cost beyond the daily launch count, or how often I act on what the town shows. No revenue is claimed.
