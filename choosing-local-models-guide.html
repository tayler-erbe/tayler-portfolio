Choosing a Local Model:
Find, Evaluate, Validate,
Fine-Tune

Model names are full of numbers that look like a ranking: 8B, 27B, 32B, 35B-A3B, Q4, AWQ. They are not a ranking. This guide explains what those labels mean, how open-weight models are commonly trained, why a smaller model can outperform a bigger one on a particular task, and a method for picking, validating and, only when needed, fine-tuning a model. It combines findings from my own evaluations, the generation model screen and the document intelligence evaluation, with general engineering guidance. Run results are specific to the configurations and cases tested; the dated pre-registrations and run records are kept with the project.

01

Reading a Model's Name

You seeIt meansWhat it does and does not tell you
27B, 32BRoughly 27 or 32 billion parameters: the numbers the model learned in trainingA design choice that sets capacity. It does not tell you how well the model was trained or how well it follows instructions.
35B-A3BMixture of experts: roughly 35 billion parameters in total, about 3 billion active per token, depending on the vendor's counting conventionSparse activation can reduce computation compared with a similar dense model, but speed depends on hardware and the serving software. All the weights still need storing. Active parameter count is not a quality score.
Q4, Q4_K_MApproximately 4-bit weight quantisation formats, with some mixed precision and storage overheadShrinks the weights so a large model fits on one card. It does not by itself shrink every other use of memory, such as the context cache.
AWQA quantisation method, not a bit widthCheck the actual bit width of the checkpoint you download. Different methods lose different things, so the same model can behave differently under each.
Instruct, chatAdapted to respond to requestsUsually the starting point for assistant-style applications. "Base" models are mainly pretrained continuation models and suit specialised adaptation.
Thinking, reasoningMay generate intermediate reasoning tokens before the final answerCan help hard problems. Whether you can see or switch off that reasoning depends on the model and server, and it costs time and token budget.
Version, release dateIdentifies a release; its documentation may disclose training changes and dataNeither size nor release date alone identifies the best model for a task.
02

How Models Are Commonly Trained

A common recipe, though not a universal one, has three stages. Vendors publish different amounts of detail, so treat this as the usual shape, not any one model's history.

01
Pretraining: next-token prediction at scale
The model learns to predict the next token over very large amounts of text and code, often trillions of tokens. Much of its knowledge and fluency comes from here.
02
Supervised instruction tuning
The model is trained on examples of requests paired with good responses, which turns a continuation model into an assistant. The quality and variety of these examples shape how precisely it follows instructions.
03
Preference optimisation or reinforcement learning
The model is pushed toward responses that are preferred. The preferences can come from people, from a reward model, or from automatic checks that verify an answer. Several different training algorithms are used for this.
Every stage affects knowledge, reasoning and instruction-following. Data, compute and all three stages matter, alongside parameter count. That is why size and release date are only starting points.
03

Why a Smaller Model Can Outperform a Bigger One

In my generation screen, Qwen3.8 27B accepted 7 of 20 test groups through a strict generator's checks, against 3 for the larger Qwen3-32B configuration it would replace. That met a pre-registered screening rule. A second pre-registered round on 60 new groups then replicated it: 24 accepted against 11, a difference of 21.7 points with a 95% interval of 6.6 to 35.5. It is still a comparison of configurations, one on Ollama and one on vLLM, on one job's groups, and adopting it remains a release decision.

A prompt review found a conflict in that task: one rule banned the phrase "each other" while another required wording containing it. Every arm in that screen ran the same pinned prompt, the one containing the conflict, copied from the release version and checked by hash, so these figures are pipeline outcomes under it, not a clean measure of either model's general instruction-following; a corrected prompt has to be versioned and re-tested on both models before any adoption. At the first plan check, the smaller model's plans were flagged by the copying check in 2 groups against 7 and by the causal-leap check in 0 against 4, but by the behaviour-only check, which also covers feelings, causes, outcomes and labels, in 9 against 0. Both were flagged by the exact-anchor check in 15 groups. These are checker flags at the first plan, not counts across retries or a semantic audit.

Newer post-training is one possible explanation. The screen did not separate it from architecture, quantisation, server, chat template or decoding differences, so it supports a configuration-level result, not a causal one.

Reasons a smaller model can outperform a bigger one on a task

Training. A different or later recipe can matter more than extra parameters. Fit to the task. Parameter count alone does not establish which model will best satisfy a task's constraints. Configuration. Quantisation, server and template change behaviour: the same 32B accepted 3 groups under one backend configuration and 1 under another. Resources. A model that fits fully on the card at the needed context usually runs faster, which matters when a pipeline retries.

And why it might not

A new model trades one set of failures for another. Only a confirmation run on new cases tells you whether the trade holds.

04

What Public Benchmarks Can and Cannot Tell You

Use them to build a shortlist

Benchmarks help when scores come from comparable harnesses, templates, budgets and decoding settings. Public test material can also find its way into training data, directly or indirectly, so treat published scores as screening evidence, not uncontaminated estimates of how a model will do on new work.

Do not use them as the verdict

In my screen, Gemma 4 had the highest IFEval score of the four models completed, 0.900 against the baseline's 0.830, and accepted 0 of 20 task groups: 3 exhausted their plan retries, 14 their writing retries, and the run's recorded refusal reasons show the other 3 stopped early after repeated failures. Qwen3.8 had the lowest of the four, 0.806, and accepted the most. IFEval measures its own kinds of verifiable instructions, not every capability a pipeline needs.

05

A Method for Picking a Model

01
Find candidates, including the licence
Start from what fits your hardware at the context, output length and concurrency you need, including the context cache and runtime overhead, then shortlist from benchmarks, recent releases and the families you already run. Check each release's licence, acceptable-use terms and commercial and redistribution rights, and any obligations that come with adapters or training data: open-weight does not mean unrestricted. Write down reliability requirements alongside speed, including how failures, timeouts and exhausted retries will be handled. Include your current model as the baseline.
02
Turn your real task into a test
Freeze a set of real cases with code-based checks or answer keys. Keep failed and timed-out answers in the denominator. Account end to end: input and output tokens, retries, runtime and cost per successful case, plus latency and throughput. If you need long inputs, test quality at that length, not just the advertised context limit.
03
Write the decision rule before you run
State the primary measure and the direction of comparison, the minimum useful improvement, the interval method and confidence level, how candidates are selected, when you will stop, and what a pass earns. Require the interval's lower bound, not just the estimate, to clear the minimum useful improvement. Count groups or cases, not retries, as the independent units. A rule written first reduces discretion; it does not remove small-sample uncertainty or the chance that one of several candidates wins by luck. Account for that with a pre-specified multiplicity procedure or an independent confirmation design, finishing candidate selection before you look at confirmation results.
04
Check harness fidelity and checker validity
Reproduce the baseline within a stated tolerance and investigate any mismatch. Separately, test the checks on known passing, failing and borderline examples, review the instructions for contradictions, and audit a sample by hand or with a validated grader. Reproducing the baseline alone does not prove the test is valid.
05
Change one thing at a time, and record everything
Run the same model under each server and quantisation you are considering, and test prompt changes separately from model changes. Record exact checkpoint and tokenizer revisions, chat template, server version, quantisation, reasoning mode, decoding settings, context and output budgets, stopping rules, retry policy and seeds. A shared seed does not guarantee identical runs.
06
Confirm on fresh cases
A screening win earns a confirmation on cases not used in local training, prompt development or model selection, with a paired interval whose lower bound clears the minimum useful improvement. You can control what you used; you usually cannot prove what a vendor's model saw in training.
06

When and How to Fine-Tune

Fine-tuning means training an existing model further on your own examples. It is an extra engineering and compute commitment, so it usually comes after cheaper levers. The costs below are illustrative.

OrderLeverTypical effortTry it when
1Fix the instructions and checksLowAlways first. Look for contradictions between rules.
2Switch or route modelsEvaluation timeA candidate meets your pre-registered rule and its confirmation. Consider a different model per stage when failures differ by stage.
3Add retrieval or toolsModerateThe problem is missing or changing knowledge, not behaviour.
4Fine-tuneHigher: data, training and validationThe best prompt and model still miss your bar, and you can produce enough good, representative examples.
Rejection-sampling fine-tuning

Automatic checks provide cheap labels for the properties they actually test. After validating the checks, sample many outputs, keep those that pass and also meet your quality requirements, and fine-tune on them. Audit coverage, diversity and signs of the model exploiting the checks. A better first-try pass rate is a hypothesis to test on held-out cases, not a guarantee.

Preference tuning

For the same request, pair a preferred and a rejected response, and make sure the preference reflects the quality you want rather than length or style. Methods such as DPO, or reward-model-based reinforcement learning, can learn from these pairs, but noisy preferences teach the wrong lesson and gains need validating.

LoRA and QLoRA: fine-tuning on one GPU

LoRA trains small low-rank adapter weights while the base model usually stays frozen; how many depends on the rank and which layers are adapted. QLoRA does the same over a frozen low-bit copy of the base. This can make some 27B training runs feasible on a 32 GB card, but feasibility must be measured for your sequence length, batch size and software. Keep the exact base checkpoint and the adapter's configuration with the adapter.

The main risk: learning the checks, not the job

A model trained to pass checks can learn to pass them while getting worse at what they do not measure. Hold out cases it never trains on, and measure general skill and quality alongside the checks.

07

How to Validate a Tuned Model

01
Split before you train, at the right level
Draw training, validation and test sets as whole cases, and split and de-duplicate at whatever level prevents leakage between related cases, documents or templates. Use validation data for tuning decisions and keep the test set untouched until the decision point.
02
Compare like with like
Run tuned and untuned models on the same base checkpoint, server, quantisation, prompt and settings. Record any differences you cannot remove, such as serving a re-quantised base.
03
Guard what the checks cannot see
Use a small regression suite covering general capabilities and your deployment needs, and a pre-specified quality review with a clear rubric, a stated sample size and sampling procedure, blinded where feasible, by people or by a grader you have validated. State the acceptable limit for each guard in advance, report uncertainty, and report important subgroup and stage-level failures, not just the average.
04
Interpret a null result carefully, then release like any change
A failed test of one recipe does not show that fine-tuning cannot help; it shows that this data, recipe and setup did not clear the bar. A tuned model that does pass still goes through your normal release route: a small live trial, a quality review and a way back.
