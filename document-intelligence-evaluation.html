Tayler Erbe · Model Evaluation Case Study · October 2026

Document Intelligence
on One GPU: Which Local Model
Reads What

Proposal packets, contracts, research awards and reports often carry their most useful facts in places that are hard to extract: scanned text, budget tables, charts, spreadsheets flattened into PDF and clauses buried on page forty. This case study defines the problem, then measures eleven open-weight models across seven tasks under a frozen protocol, then confirms the winners on data no model had seen. The deployment target is a single NVIDIA L4 or L40S. It uses public benchmarks only. Every score comes from reference answers and code, never from another model's opinion.

01

The Problem

Most organisations already have the information they need. It sits in document packets: a procurement proposal with a pricing table and a scanned signature page, a research proposal with a budget spreadsheet printed to PDF, a contract with renewal terms in an amendment, a technical report with a key result shown only in a chart. All of it can be read by hand. A database cannot read it, and neither can a search box.

Plain prose is rarely the problem. The problem is the hard-to-reach information: numbers in tables, values shown only in a graph, text in images and scans, fields split across pages, and the exact sentence that supports an answer. A single document needs several kinds of extraction at once. Each kind fails differently.

Cloud document services solve part of this problem, but many of these documents cannot leave the organisation. That makes the question narrower and more useful: on a GPU an organisation already has, which open model can be trusted with which part of a document, and how would you know? This evaluation was built to answer that question with reproducible numbers.

What "solved" has to mean

An extracted record is useful only when the numbers are right, the source page is attached, and the system says so when it is unsure or could not read a page. Fluent text that is 90% right is a liability in a budget.

Five kinds of extraction in one packet

Running text from scans · tables with amounts · charts and graphs · spreadsheets rendered to PDF · clause-level evidence for a question. Each needs its own test and its own metric; a single "accuracy" number hides the one that matters.

Constraints

One model on the GPU at a time. A single data-centre GPU, an L4 (24 GB) or an L40S (48 GB), as the deployment target; every model measured on one 32 GB desktop so speeds compare fairly. No model grades another model. Failed and truncated answers stay in the denominator as zero. Public datasets only, so every number here can be published and checked.

Supplier packets that mix a cover letter, line-item pricing tables, delivery terms and scanned compliance forms.

03

Method — Rules That Make the Numbers Comparable

The desktop and the laptop ran weeks apart under different runtimes. For their results to merge into one report, "the same test" had to be checked in code rather than promised. A conformance check fingerprints the frozen case manifests, the exact requests each task sends to a model, the model-call settings and the scorers, and the merge tool refuses rows that fail it.

01
Freeze the cases before any model sees them
Development sets were selected and hashed first; held-out confirmation sets (2,181 cases in round 1, 1,988 in round 2) were frozen separately and used once. "Fresh" means unused in earlier runs, not proven absent from pretraining.
02
Send identical requests
Same prompt, JSON schema, token budget (300 to 6,000 by task) and image cap (1,600 to 1,800 px) for every model. Temperature 0, instruct builds only. A thinking build burns the budget on hidden reasoning and gets cut off, so one was removed and its rows deleted.
03
Score with answer keys and code
Character error, TEDS, relaxed accuracy, value recall and word F1 are computed against the datasets' published references. No model grades another model. Truncated or failed answers score zero and stay in the denominator; nothing is re-run to rescue it.
04
Pre-register, then confirm
Round 2 picked its confirmatory method (vote3) on development data, wrote the decision down, then ran the held-out charts and pages. Paired bootstrap intervals and McNemar tests with Holm correction come from the same frozen code on both machines.
05
Merge only what conforms
Each export carries its case hashes, model digests and conformance result. The merged report marks a cross-machine comparison as a reproduction only when the weights match; the 8B digest differed between machines, so that pair is labelled a method comparison.
Division of labour

Local models did all the reading, extraction and answering. AI coding assistants wrote and ran the harness. No assistant read a page, a crop or a model answer; people read aggregate tables only.

Do the two machines agree?

Qwen2.5-VL 7B ran with identical weights on both. 11 of its 13 comparison groups reproduced under the report's rule; the two that disagreed were a 200-question chart prompt variant (+3.0 points) and a 60-case chart-to-table variant (−14.8 points).

04

Findings — A Different Route for Each Task

There is no universal winner. Small specialised parsers lead on tables and page text, the method matters as much as the model for charts, and every trick that makes text cleaner has to be checked against the numbers it loses.

Final round: small parsers, confirmed on fresh data

The last round tested four models never run before in this evaluation: three small document parsers (Nemotron 3.5 Parse, PaddleOCR-VL-1.6 and olmOCR-2 7B) for pages and tables, and gpt-oss-20b for clauses. The two leads it found were written down as hypotheses first, then tested on sets no model had seen in this project: 100 financial-report tables from FinTabNet.c and 80 unused OmniDocBench pages, every model at the same 8,192-token output budget, against Qwen3-VL 32B AWQ.

A hypothesis passed only if its main metric improved and numeric recall was no more than 0.02 worse, under a source-clustered bootstrap with Holm correction. PaddleOCR-VL-1.6 passed. Nemotron Parse wrote better page text and tied the 32B on numbers on average, but 80 pages cannot rule out a 0.02 deficit, so it counts as a lead, not a win.

Fig. 01 — Chart questions, 200 development cases. The same self-check instruction moves 7B up 26.5 points and 8B down 43.5.

On the text tasks, model size made little difference. The 8B model's pooled character error on 50 prose crops was 1.2% on both machines. That matched Qwen3-VL 32B AWQ and Qwen2.5-VL 32B on the desktop. Qwen2.5-VL 7B scored 2.0% and 1.8%. Table transcription followed the same order: 8B scored 0.818 TEDS, compared with 0.821 for the 32B AWQ build and 0.724 for 7B. No prompt variant changed the table result significantly.

That is good news for the 12 GB target, but one caveat drives the rest of the project. Every model, large or small, recovered 96.5% of the numbers in the crops. For budgets and invoices, the missing 3.5% is the whole problem. That is why the evaluation treats numeric recall as its own gate rather than folding it into a text score.

Fig. 02 — Crop OCR and table transcription by model and machine, development set.
Round 2: confirming on charts nobody had used

Development scores on 200 questions can make a method look better than it is. Round 2 froze 1,322 new questions across 722 charts and 80 new pages. It selected vote3 (three answers, majority wins) in advance as the one confirmatory method. Everything else ran as a supporting comparison.

Vote3 held up: +4.5 points on 7B (95% interval +3.0 to +6.1) and +2.6 on the desktop 32B (+1.4 to +3.7). On 8B it did nothing (−0.2, interval crossing zero). Self-check's development pattern also held on the fresh charts: +17.8 for 7B, −42.7 for 8B. Read-table-first was dropped on development data. Upscale alone did not help.

The costs differ. Self-check is one longer call. Vote3 is three calls. For a 7B deployment, self-check is the cheap win and vote3 is the expensive one. For 8B, neither applies. For 32B, vote3 is the only confirmed gain.

Fig. 03 — Round-2 confirmation on held-out charts. Intervals are paired bootstrap, 95%; questions on the same chart are correlated.
Whole pages: the masking trade-off
Fig. 04 — Layout masking on Qwen3-VL 32B AWQ. Word F1 up, numeric recall down, on both page sets.

Figures and tables confuse whole-page OCR, so in round 2 I used a layout detector to blank them first. The prose got cleaner: word F1 rose from 0.814 to 0.881 on the 80 confirmation pages for the desktop 32B, and 7B gained +0.085 on the laptop. 8B gained +0.010, with an interval that includes zero.

But masking also hid numbers needed in the page text. Numeric recall on the same 80 pages fell from 0.872 to 0.694, and from 0.909 to 0.720 on the 40 development pages. Results for newspapers got worse. That trade is unacceptable for contracts and budgets, so masking stays experimental: the next version will blank only tables, figures and equations, and I will judge it on numeric recall first.

Do not trade numbers for cleaner prose. A method that raises the headline text score while silently dropping amounts is a regression for every application on this page. Numeric recall is reported beside every text metric for that reason.

Beyond OCR — Evidence-Linked Extraction

Reading the page is half the job. For contracts and proposals, the answer to "what is the termination notice period?" needs the sentence that proves it. Early legal runs on public contract datasets exposed a specific failure: models quoted text that did not exist in the cited span, or paraphrased it enough to fail a string check. A quote you cannot find is worse than no answer.

The fix takes copying out of the model's hands. Source documents are split into blocks with IDs. Retrieval supplies candidate blocks. The model returns only the IDs and the label. Application code then copies the exact text, verifies its hash and location, and records absent fields explicitly. In the public legal tests, this removed every copy failure produced by the quoting design (0 failed requests against 2 to 4 for the baseline). The remaining gains came from handling fields that are genuinely absent.

This does not prove the answer is right. Mechanical provenance and semantic correctness are separate checks. That is why the legal track reports strict correctness, accepted responses, evidence F1, retrieval coverage and truncation in separate columns rather than as one score.

Evidence by ID

Model selects block IDs → code copies the source text → hash and offset verified → absent fields recorded as absent → human reviews with the page beside the answer.

Known limit

Retrieval is the bottleneck. When the right block is not among the candidates, no evidence design can recover it; coverage has to be measured and shown, not assumed.

Configuration, not verdict: the Nemotron reassessment
Fig. 05 — Reasoning on versus off, 60 public legal documents not used in earlier runs. Strict correctness and accepted responses, out of 30 per task.

A hosted Nemotron 3 Nano 30B endpoint scored far below the local Qwen models on the first pass. The easy conclusion was "weak model". The honest one was "weak configuration, untested". A controlled reassessment ran 192 requests across eight configurations on the same 24 cases. It changed one mechanism at a time: output budget, reasoning, sampling, label definitions, full-document context, evidence by ID and schema delivery.

Budget alone changed nothing. Enabling reasoning at the same budget lifted CUAD from 1/12 to 4/12. A pre-specified contrast on 60 fresh documents then confirmed the direction. With reasoning on, strict correctness rose from 3/30 to 13/30 on CUAD and 5/30 to 12/30 on ContractNLI. The cost was one truncation per task, which counts as zero.

That supports enabling reasoning for further work. It does not establish production adequacy or a serving defect. In the final comparison on the same 60 documents (table above), it trailed Qwen3 32B on ContractNLI. On CUAD, no configuration beat the always-absent baseline of 15 out of 30. A poor result without a controlled comparison proves nothing about the model family. The reassessment was designed to avoid drawing conclusions about the model family or a serving defect by accident.

The Hardware Constraint

The deployment target is a single data-centre GPU: an NVIDIA L4 with 24 GB or an NVIDIA L40S with 48 GB. Fit follows from measured weight sizes. The two recommended parsers need about 2 GB (PaddleOCR-VL-1.6) and 1.3 GB (Nemotron 3.5 Parse), gpt-oss-20b about 13 GB, and a 4-bit 32B model about 20 GB. Every recommended model fits an L40S. On an L4 the parsers and a 20B-class legal model fit with room for context, while a 32B model is tight.

Every final-round model ran on one RTX 5090 desktop with 32 GB, so speeds compare fairly with each other. On one packet of 20 pages and 20 tables, four requests at a time, Nemotron Parse processed 140 cases a minute, PaddleOCR-VL-1.6 73, olmOCR-2 19 and Qwen3-VL 32B AWQ 9. Absolute speeds on the target cards will be lower. Token generation is limited by memory bandwidth, about 1.8 TB/s on the desktop, 0.86 TB/s on an L40S and 0.3 TB/s on an L4. The 32B models are hit hardest, so the parsers' lead should hold or widen.

Weights are only part of the memory budget. Context length, image preprocessing on the CPU, runtime overhead and any concurrency all need headroom. The runtime can silently push layers to the CPU when memory runs out. Every run was checked to be fully on the GPU before it counted. The chart on the right comes from the earlier rounds, which also ran on a 12 GB laptop GPU.

08

What This Means for the Problem

Back to the packet. The intended workflow identifies document types, recovers text and tables, proposes defined fields, attaches page-level evidence, flags missing or uncertain information, and exports approved records. The evaluation shows which parts are ready for a review-assisted prototype on a single L4 or L40S and which are not.

Ready to prototype: tables with PaddleOCR-VL-1.6, whole-page text with Nemotron 3.5 Parse plus a numeric check, prose crops with the 8B model, chart questions with a method chosen for each model, and evidence-by-ID clause extraction with Qwen3 32B or gpt-oss-20b. Not ready: unattended numeric extraction (no model reached the 99% bar; the best table route reached 97.4%), whole-page masking where numbers matter, and any claim about an organisation's own documents until a labelled, document-disjoint test exists for those documents.

Native spreadsheets should be parsed directly whenever the original file exists. A spreadsheet rendered into a PDF needs the table route and a numeric check. Multi-page packet segmentation, chart interpretation and field validation each need their own gate.

Keeping documents local

Where policy or contract forbids external processing, a local pipeline keeps content inside an organisation-controlled environment. That is an architectural option, not a security certification: access control, encryption, logging, retention and network egress still have to be implemented and verified. NIST AI 600-1 is the risk framing used here.

Routing, from the measured results

Tables → PaddleOCR-VL-1.6, single pass · Whole pages → Nemotron 3.5 Parse, single pass, numbers checked · Prose crops → Qwen3-VL 8B baseline · Chart questions → 8B with self-check off, or 7B with self-check on · Chart to data → 8B self-check · Layout → DocLayout-YOLO · Clauses → Qwen3 32B with thinking off, or gpt-oss-20b at low reasoning, with evidence by ID and retrieval coverage shown.

Engineering Takeaways

01
Define the problem as extraction types, not "OCR"
A packet needs text, tables, charts, flattened spreadsheets and clause evidence, and each one fails differently. Six tasks with six metrics found a 43-point swing that a single accuracy number would have averaged away.
02
The method is part of the model
Self-check helped 7B by 26.5 points and hurt 8B by 43.5 on identical inputs. Route methods per model and task, and confirm each pairing on data it has not seen.
03
Keep failures in the denominator
Truncated and failed answers score zero and are never re-run. That rule is what made the thinking-build collapse and the first Nemotron result visible instead of quietly "fixed".
04
Report numbers beside text
Masking raised word F1 by 0.067 and cut numeric recall by 0.178 on the same pages. Any document workflow that handles money needs numeric recall as its own gate.
05
Separate provenance from correctness
Letting code copy the evidence removed every copy failure; it did not make answers right. Show both, and show retrieval coverage, so a reviewer knows which kind of wrong they are looking at.
06
A bad score is a configuration until proven otherwise
One controlled reassessment, one mechanism at a time, turned a 1/12 into a 13/30-versus-3/30 reasoning contrast. Conclude about the model family only after the configuration has had its fair test.
