Tayler Erbe · Model Evaluation Case Study · October 2026

Rule-Bound Generation
on One GPU: Which Local Model
Follows the Rules

A text generator that must pass its own automated checks is only as good as the model's ability to follow instructions exactly. When my generator's yield stalled, the question became whether a different local model would do better. This case study measures seven open-weight models on the generator's own checks, under a decision rule written before the run, and sets a public instruction-following benchmark beside it. Speed and memory are measured the same way for every model on one RTX 5090. No model grades another.

01

The Problem

Skyrule, my self-funded personal project, writes a library of short structured readings with a local model. Each piece is made in stages. The model first writes a plan, then writes the piece from the plan, and code checks every plan and every piece before anything is kept. The checks are strict on purpose. A claim must use the exact wording it is anchored to, two claims may not copy each other, and a suggestion must rest on a supported input.

A trial run on 20 frozen test groups ran cleanly but kept only 3 of 20 groups. That was far below the bar of 9. Every first plan failed at least one check, with a median of five failing checks per plan. Tracing the prompts showed the required words were reaching the model. The model simply was not following the instructions it had been given.

That makes the question narrow and testable: with the prompt, the checks and the bar held fixed, does a different local model follow the rules better, and by how much?

What "better" has to mean

More groups that pass every check, without passing fewer on the first try. Fluent writing that fails a check is a rejected piece, so the generator's own checks are the score.

Constraints

One model on the GPU at a time. No change to the prompt, the checks or the bar for any model. Rejected and timed-out work stays in the denominator. No piece text appears anywhere in the reporting, only counts and check names.

03

Method

01
Write the decision rule before the run
The rule was frozen by hash before any model loaded. The bench counts only if the current model reproduces the trial run within two groups. A candidate earns a full trial only if it beats the current model by at least four accepted groups and does no worse on first-try acceptance.
02
Run the real generator, not a copy of the idea
Each arm ran the release generator's own code, prompt, retry budget, seed and checks on the same 20 frozen groups, pointed at a different model. Only the server and model changed. Every file's hash was checked against the release tree.
03
Refuse a model that does not fit
A model that spills off the GPU runs slower and changes the result, so each arm had to load 100% onto the card at the same context length, or it was refused. All seven fit.
04
Guard the GPU like a shared lab bench
The bench held a lock on the card, checked it still owned the card before every destructive step, and watched for any model it had not loaded. It always restored the machine's resident service at the end. When a scheduled morning job loaded its own model mid-run, the watcher stopped that arm and marked it contaminated instead of reporting a number.
05
Put a public benchmark beside the private one
IFEval (541 prompts with verifiable constraints) was scored with its reference checker, which was first validated against the paper's published answers. The two kinds of result are reported side by side and never mixed into one number.
06
Have the design reviewed before spending GPU time
An independent reviewer model read the design twice. Its first-round demands (a lock held across load and restore, ownership checks, restores that wait, and race tests) were all built and tested on CPU, 67 tests in all, before the card was touched.

No model passed a group on its first try, so first-try acceptance was 0 of 20 for every arm. Qwen3.8 against the current model, group by group: both passed 2, only Qwen3.8 passed 5, only the current model passed 1 (exact McNemar p = 0.22, reported, deciding nothing).

The serving setup matters as much as the model

The same Qwen3-32B kept 3 groups on vLLM with AWQ and 1 group on Ollama with Q4, and spent three times the calls doing it. A model comparison that changes the server at the same time is measuring two things at once.

Different models fail at different stages

Gemma 4 was the best planner in the group: its plans were rejected for only 3 groups, against 15 for the current model. But every piece it wrote then failed the writing checks, so it kept nothing. Qwen3.8 was the reverse, with middling plans but pieces that pass. One model per stage is a design worth testing.

Efficiency moved more than yield

Qwen3.8 needed about half the model calls and a quarter of the output tokens per accepted group. On a single card that matters as much as the pass count, because it sets how long a full library takes to write.

Seven still miss the bar

The best result, 7 of 20, is still below the bar of 9. A better model narrows the gap; it does not close it. The remaining failures cluster on two exact-wording checks for every Qwen model, which points back at the instructions as well as the model.

Why the Smaller, Newer Model Won

Qwen3.8 27B is smaller than the current Qwen3-32B and still kept more than twice as many groups. The run records show where the difference came from, stage by stage, on the same 20 groups.

It said less, so it broke fewer rules

Its plans were about a third shorter. Every extra sentence in a plan is another chance to copy a claim, overreach or miss a required word. Under strict checks, concision is a skill, and the newer model had more of it.

It followed the specific rules better

Copying between claims fell from 7 groups to 2, and cause-and-effect leaps disappeared. Plans passed sooner, so the generator reached the writing stage for more groups, and once there, the pieces passed.

Size was not the driver; the generation was

Qwen3.8 is a later release of the same family. The likeliest explanation is newer instruction training that handles many simultaneous constraints better. On the same server the gap is even larger: the 32B kept 1 group on Ollama against the 27B's 7, so the current model was being helped by its vLLM setup.

What it did not fix, and what it made worse

Both models failed the exact-anchor-wording rule on the same 15 groups. That points at a contradiction in the instructions, not at the model, and a prompt fix is prepared separately. The 27B also slid from behaviour into feelings or causes more often. A new model trades one set of failures for another; it does not remove them.

These are behaviours measured in the run records. The reasons behind them, such as training data and instruction tuning, cannot be observed from outside the model and are stated as the likeliest explanation, not as fact. With 20 groups, the two models' intervals overlap, which is why the result earns a full trial rather than a switch.

The public score pointed the wrong way. Gemma 4 led IFEval clearly (0.900 against the current model's 0.830; it passed 61 prompts the current model failed and failed only 23 it passed) and kept nothing on the generator's checks. General instruction-following measures something real, but not the thing this generator needs; the only reliable test of a rule-bound generator is its own rules.

Do you need to download another model?

Not yet. The leading candidate was already installed, and the two newest models I downloaded for the test did not beat it. The next information comes from repeating the winner on another seed and more groups, and from testing one model per stage, not from a wider search.

08

Engineering Takeaways

01
Measure the task, then read the leaderboard
Two models tied on IFEval and differed on the real checks. A public benchmark tells you which models to try; your own checks tell you which one to use.
02
Prove the bench before trusting it
The bench only counted because the current model reproduced the trial run exactly. Without that check, a difference between arms could have been a difference between harnesses.
03
Separate the server from the model
Changing only the server and quantisation moved the same model from 3 to 1 accepted groups. Any model switch needs that control arm.
04
Decide before you look
With seven arms and 20 groups, one model can clear any threshold by luck. Writing the rule down first, and treating a pass as "earns a full trial" rather than "adopt", kept a screening result from becoming a decision.
05
A shared GPU needs a lease, not good intentions
A scheduled job on the same machine loaded its own model during the run. Because the bench watched for that, the arm was marked contaminated instead of producing a wrong number, and it was re-run in a clean window.
09

Next

Full trial of Qwen3.8 27B. It goes through the same release route as any change: its own canary run and an independent quality review, on more groups and another seed. A screening pass is not an adoption.

One model per stage. Plan with the strongest planner and write with the strongest writer, measured against the same checks.

The instructions themselves. The same two exact-wording checks dominate the failures across the Qwen family, and a fix to the prompt is already prepared as a separate candidate. Model choice and prompt choice will be tested one at a time, so each effect stays visible.
