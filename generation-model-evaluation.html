Tayler Erbe · Model Evaluation Case Study · October 2026

Rule-Bound Generation
on One GPU: Screening Local
Models Honestly

A text generator that must pass its own automated checks depends on two things together: a model that follows instructions, and prompts and checks that do not contradict each other. When my generator's yield stalled, I screened seven model configurations covering six local models on the generator's own checks, under a decision rule written before the run, and set the public IFEval benchmark beside it. This page reports what was measured, what was not, and what can and cannot be concluded from it.

01

The Problem

Skyrule, my self-funded personal project, writes a library of short structured readings with a local model. Each piece is made in stages. The model writes a plan, then writes the piece from the plan, and code checks every plan and every piece before anything is kept. The checks are strict on purpose: a claim must use the exact wording it is anchored to, two claims may not copy each other, and a suggestion must rest on a supported input.

A trial run on 20 frozen test groups completed within its bounds but kept only 3 of 20 groups, against the project's pre-registered bar of 9. A separate measurement found that every first plan failed at least one check, with a median of five failing checks per plan. It also reconstructed the prompts and found the required anchor words present for all 20 groups, and it found a contradiction: one rule banned the phrase "each other" while every accepted wording of one goal contained it.

So the low yield could come from the model, the serving setup, the instructions, or all three. This screen asks one narrower question: with the prompt, checks and bar held fixed, does another local model configuration accept clearly more groups, enough to justify a full trial?

What "clearly more" has to mean

At least four more accepted groups than the current configuration, without fewer accepted on the first try, decided before the run. Fluent writing that fails a check is a rejected piece, so the generator's own checks are the score for this screen. They do not measure writing quality beyond what they test.

Constraints

One model on the GPU at a time. No change to the prompt, the checks or the bar for any arm. Within each completed main arm, rejected and timed-out groups stay in the denominator of 20. Only counts and check names are reported, never generated text.

03

Method

01
Write the screening rule before the run
Frozen by hash before any model loaded. Fidelity gate: the baseline must reproduce the trial run's 3 of 20 within two groups, or nothing is concluded. Screening rule: an arm earns a full trial if it accepts at least four more groups than the baseline and does not accept fewer on the first try. The four-group margin is a screening threshold with no calibrated false-positive control across several candidates.
02
Run the real generator
Each arm ran the release generator's own code, prompt, retry budget, seed and checks on the same 20 frozen groups, pointed at a different model configuration. The bench's records show each copied file's hash checked against the release version.
03
Require a full fit on the card
Every Ollama arm had to load 100% onto the GPU at a 16,384-token context, or it was refused. All six Ollama arms did. The vLLM baseline ran on its own server; its fit was not checked the same way.
04
Guard the GPU and refuse unsafe restores
The bench held a lock on the card, checked ownership before destructive steps, watched for any model it had not loaded, and stopped an arm when one appeared. It refused to restore the machine's resident service while it did not own the card. Restores did not always succeed; see the incident record below.
05
Put a public benchmark beside the task
IFEval was scored with its reference checker. Before use, the checker reproduced the paper's published GPT-4 results within a tolerance of two prompts and two instructions on all four metrics; it was not an exact match. Two rows draw a random letter; the draw was seeded identically for every arm.
06
Review the design before spending GPU time
An independent reviewer model read the bench design over two rounds; its first-round requirements were built and covered by 67 CPU tests before the card was used. A later independent audit of this write-up found overstatements, which are corrected on this page.

C met the rule: seven minus three is four more accepted groups, and first-try acceptance was 0 of 20 for both, so it did not lose. Paired by group, C and A both accepted 2, only C accepted 5, only A accepted 1 (exact McNemar p = 0.22, unadjusted, descriptive). The marginal intervals describe uncertainty in each arm's rate; they are not a test of the paired difference. With 20 fixed groups and one seed, these results say little about small differences or about other groups. "Calls" and "output tokens" per accepted group are success-normalised totals across all stages of this run, not measured completion times.

Backend configuration is part of the comparison

The same Qwen3-32B accepted 3 groups on vLLM with AWQ and 1 on Ollama with Q4_K_M. Total calls were about equal, 102 and 104, so per accepted group B used about three times as many. Server, quantisation and possibly template and sampling defaults changed together. In this single run the two bundles differed; the screen does not show how reproducible that is, or how much the server alone contributes.

Failures differed by stage

Gemma 4 had 3 groups rejected at the plan stage and 14 at the writing stage, across 42 writing calls, and accepted none. The current configuration had 15 groups rejected at the plan stage. This suggests testing a different model for each stage. It does not establish which model plans or writes best.

Resource use per accepted group fell sharply

C used about half the model calls and about a quarter of the output tokens per accepted group in this run. On a single card that matters, but full-library time also depends on batching, latency and how yield varies across other groups.

Still below the bar

The best result, 7 of 20, is below the project's bar of 9. A better configuration, if confirmed, would narrow the gap, not close it. The instruction contradiction still needs its own repair and test.

What the records show

C's plans were about a third shorter on average and it needed fewer plan calls. At the first plan it was flagged less often on DUP1, GOAL1 and LAUNDER2, and more often on NEV1. These are checker flags at the first plan, not a full semantic audit or counts across retries. Both had 15 groups fail BF8 at round 0; the counts do not show whether they were the same groups.

What the records do not show

This screen compares configuration bundles. It does not isolate training, model size, architecture, chat template, quantisation, sampling or run-to-run variation, so it cannot say which of them produced the difference. Shorter plans coincided with fewer flags on some checks; the screen does not show that shortness caused it.

Hypotheses worth testing

Newer instruction and preference training in the later release; more concise output under strict checks; a better fit between the model and its chat template. Each is a hypothesis, not a finding. A repeat on a new seed and more groups is queued as the next evidence.

The instruction conflict sits under every arm

Because one rule banned a phrase another required, some failures may reflect incompatible instructions rather than either model. The aggregate BF8 counts do not identify how much of the failure that conflict caused. A candidate fix is queued for a separate test.

IFEval and the generator's checks measure different things: general verifiable instructions versus this task's specific rules. Neither alone establishes writing quality or fitness for release. In this study, the task checks and a pre-registered rule decided which configuration earned a full trial.

09

Engineering Takeaways

01
Measure the task as well as the leaderboard
Here the IFEval ranking and the task ranking differed. A public benchmark is useful for building a shortlist; in this study, the task's own checks and a rule written in advance decided which configuration earned a full trial.
02
Check the harness and the instructions
The baseline reproduced the earlier run's count, 3 of 20, which is what the fidelity gate requires. That does not prove the harness, checks or prompts are sound; a separate review found a contradiction in the instructions.
03
Compare bundles, and say so
The same model accepted 3 groups under one backend configuration and 1 under another in this run. Any model comparison is a comparison of model, server, quantisation and template together unless those are separated.
04
Decide before you look, and keep the decision small
With seven arms and 20 groups, one arm can clear a threshold by luck. A rule written first, and a pass that earns only a full trial, kept a screening result from becoming an adoption.
05
A shared GPU needs isolation, not just good timing
Moving a window earlier did not remove the interference that contaminated it. The watcher caught both events and the affected results were discarded; round 2 now coordinates with the other job instead.
06
Have the write-up audited too
An independent audit of the first draft of this page found causal claims the data did not support, a units error and figures from the wrong window. The corrected page says less and is more defensible.

Next

Round 2, queued, not yet run. A repeat of the baseline against Qwen3.8 27B on a new seed and more than 60 new groups, under a new pre-registered rule with a paired interval; a two-by-two of model and prompt, using a candidate fix for the instruction contradiction; a staged test in which Gemma 4 plans and Qwen3.8 writes; and the missing IFEval and speed arms.

A small fine-tuning experiment, designed and pre-registered, not yet run. Training Qwen3.8 27B on its own check-passing outputs, with test groups split off by whole job, a pre-registered rule, and guards on IFEval and an independent quality read. A null result would be specific to that recipe.

Adoption only through the release route. Any change still needs its own canary run and an independent quality review. Level 2 research only: nothing on this page is release validation.
