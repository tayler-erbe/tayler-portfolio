01 / Agent Organization

A company made of agents

I designed the build team as a 15-agent AI engineering organization: fourteen departments plus a Principal Architect, modelled on a real company. The departments cover the domain practice, relational science, editorial, product design, platform and data engineering, AI and performance engineering, QA and compliance, data science, brand and marketing, legal and trust, finance and operations, program management, the office of the founder, and security and IP protection.

Each agent is a Claude Code subagent with a written charter, a scope of work, a handoff protocol, persistent memory and an explicit list of what it does not own. Changes that cross departments route through the Principal Architect for integration review.

Lanes enforced by tooling, not by instruction

"Agents should stay in their lane" is easy to write in a prompt and easy for a model to ignore. Code ownership is defined in a machine-readable map and enforced by the tooling, so an agent cannot change files outside its own scope. Least privilege becomes a control rather than a request.

Decision continuity
Founder decisions recorded verbatim in an append-only log; agents read it before asking a question that has already been answered
Session continuity
Mission file, open-threads register, handoff documents and a coordinator brief let any new agent session resume without loss
Code review
29 pull requests from a cloud engineering agent reviewed and integrated: isolated checkout, full test suite and regression controls before any merge is reported
02 / Orchestration

Work that runs while I sleep

An autonomous job queue and GPU scheduler (Python, on a 15-minute tick) runs the long work: separate lanes for CPU, local-model and cloud-model jobs, priorities, dependencies, start conditions, finish checks, retry limits, a usage-budget guard, and automatic pause-and-resume when a model usage limit is reached. It has launched 650+ unattended jobs since early October 2026, including overnight GPU extraction runs and parallel multi-agent research batches.

Each task goes to the cheapest model that meets its quality bar: frontier Claude models for reading, verification, design and audit; local open-weights models on my own GPU for high-volume generation, extraction and grading; small local models for routing and utilities. Every model was measured on the actual hardware before it was given a role, rather than chosen by reputation.

04 / Provenance

Every number traces to a source

Underneath the product is a deterministic chart engine written in Python, exposed through a versioned FastAPI layer, with regression controls that must reproduce 279 reference spans exactly. On top of it sits a sourced-rule pipeline over a 76-title licensed corpus: whole-chapter extraction, independent verification by a second model, a verbatim-quote gate, page re-checks, quarantine, and staged release into a rule store.

4,256 verified rules were released for use on October 6, 2026. Every number in the product traces to a rule, a page and an engine event.

An interpretable model with no scoreboard

The relationship model is specified as explicit functions, gives one value per goal per kind of relationship, and holds every weight in a ledger with a stated basis, marked provisional until data science calibrates it. A product rule is enforced in code and tests: no total, ranking or compatibility score, even internally.

05 / Generation

The model proposes; code checks every claim

The content generator is brief-first. Code lays out what the inputs support; the local model plans a reading claim by claim; code validates every claim; then the model writes one sentence per approved claim and code checks again. Nothing reaches the library on the model's word alone, and the founder reviews before anything is released.

I iterated the validator through seven versions from my own reviews, adding checks for truncated claims, unsupported causal leaps, attributing a trait to the wrong person, and claims the inputs do not establish. Every new check is tested before use three ways:

TestResultWhat it shows
Named defects8 of 8 caughtThe validator catches the failures I identified in review
Previously accepted claimsfalse-alarm rate reportedA stricter check does not silently reject good output
Mutation testing21 of 21 caughtDeliberately broken inputs are detected

An end-to-end pilot on the 32B model ran against pass conditions set before the run. It showed that an over-literal check was rejecting acceptable text. Fixing the prompt and the check raised plan acceptance from 6 of 31 to 14 of 31 and usable output from about 690 to about 1,280 pieces per GPU-hour.

06 / Evaluation

Grading 2.6 million pieces honestly

Grading a 2.6-million-piece library three times over was measured at about 5,600 GPU-hours, which is not feasible. The grading strategy replaces it with statistical lot acceptance sampling (exact binomial plans with stated producer and consumer risk), code checks on every piece, brief-level grading before expansion, and a plan for a distilled grader.

Every quality bar is set before measurement and reported as both a point estimate and a Wilson 95% lower bound; for example, a precision gate passed at 84 of 96 (87.5%). An independent model labels claims in each batch, its agreement with my verdicts is measured, and the labels become a regression set for the validator.

07 / Governance

Quality, security and data protection

Quality governance
A register of quality bars with proof each was set before measuring, the authority to block on quality with a written reason, a weekly quality review, and re-runnable evidence required for every "done" claim
Security & IP
A dedicated security and IP-protection function with the authority to block any merge or release that weakens a control, and a weekly security review
Privacy by design
Users' personal chart data is never sent to a cloud model and never appears in code, tests, logs or commits; fabricated fixtures only. Consent is the gate for storing anyone else's data
Rights
Licensed book text stays out of the repository, with rights records and a quote-permitted gate
Engineering practice
1,375 automated tests passing on the integration branch (October 12, 2026), known-bad controls that must fail, and a release gate that fails on any unapproved input change
