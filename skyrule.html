01 / What Skyrule Is

A sourced-rule inference system

Skyrule helps a person understand themselves and the people in their life, and see how those relationships move through time on a calendar and a timeline. Astrology is the interpretive lens. The engineering problem is a data problem: source a formal set of rules from original texts, encode them, and apply them to each person's chart as the sky changes.

Underneath it are four parts. A deterministic astronomical chart engine. A rule store in which every rule traces to a book, a page and a verbatim quote. A per-goal relationship model that deliberately never produces a total, a rank or a compatibility score. And a locally hosted LLM content pipeline gated by automated validators, statistical acceptance testing and my own review. I conceived the product, designed the system and run it day to day as founder, product owner and technical lead.

02 / Source Material

It starts with the books

Every rule in the product starts in a primary source, not a modern summary. The rule pipeline runs over a 76-title licensed corpus. Alongside it I read 170 scanned early printed books, about 22,700 pages, printed from the 1480s to the 1850s: Latin, early-modern English with old spelling, gothic type, and a few in Hebrew, Persian and Greek, with multi-column layouts, tables, diagrams and woodcuts.

The text layers that came with the archive scans had destroyed every astrological symbol, so the pages had to be read again from the images, on one self-hosted GPU workstation with open-weights models. That work has its own case study: Historical book OCR.

03 / The Rule Store

Every rule traces to a book, a page and a quote

I built Skyrule with a deterministic Python chart engine underneath, exposed through a versioned FastAPI layer. The engine must reproduce 279 reference spans exactly for regression control. Above it runs a sourced-rule pipeline over a 76-title licensed corpus. The process starts with whole-chapter extraction, followed by independent verification from a second model, then a verbatim-quote gate, page re-checks, quarantine, and staged release into a rule store.

I built Skyrule to trace every number in the product to a rule, a page, and an engine event. On October 6, 2026, I released 4,256 verified rules for use.

The natural unit is a signification: a sentence in a source that says what a condition in the sky means for a person. The pipeline turns each one into a structured rule with seven required parts: the trigger (the sky or chart condition), the natal target that makes it personal, the timing, the themes, the modifiers, the source (author, book and page) and the tradition. For example, William Lilly writes, "If Saturn transits the ascending degree, he excites the native to gravity, to soberness, to melancholy." That becomes a transit rule: Saturn, conjunction, natal Ascendant, with its effects and its uncertainty recorded.

Three layers are kept apart and never merged: the author's exact words, the structured paraphrase, and the research tags that say which behaviors a passage supports. On October 9 and 10 I extracted and verified 1,242 more rules from five books, of which 525 were cleared after a rights review.

04 / The Relationship Model

One value per goal, never a score

The model describes people with ten behavioral dimensions: closeness, independence, communication, emotional sensitivity, ambition, assertion, steadiness, care, play and repair. It reads a relationship through six goals: be closer, be understood, be taken seriously, give them room to shine, be able to count on each other, and keep things easy. Between two people it looks for eleven named interaction mechanisms, each with two directed sides, because what one person experiences is not what the other does.

It is specified as explicit functions. A person's state at a given time is a function of two things: their natal chart, which is fixed, and the current sky, which changes every day. A pair's dynamic is a function of both charts and both states. The output is one value per goal for each kind of relationship, because what someone wants from a partner differs from what they want from a co-worker or a sibling, and a goal that does not exist for a relation kind is refused.

There is no total, ranking or compatibility score, even internally, and that rule is enforced in code and tests. Difference is information, so the writing never calls a relationship bad. All 206 weights sit in a ledger with a stated basis, and all 206 are marked provisional: none is calibrated yet. The prototype passes 120 checks and kills 22 of 22 deliberate mutants.

05 / Time

The same two people, different on different days

The sky keeps moving, so the model is a time series. A moving planet makes an aspect to a point in someone's chart (a transit), the chart advances one house per year of life (a profection), the sun returns to its natal position (a solar return), and progressions advance the chart symbolically. The unit is an episode: one moving body making one aspect to one natal point, from entering orb to leaving it, with its exact day.

The same event lands differently in different charts, so the same two people have different dynamics at different points in time. Measured on one invented chart across 2026, 365 of 365 days had at least one active episode, and the active set changed on 321 of 364 days (88%). The product shows this as a ladder: the sky, what it activates in you, who else in your circle the same sky touches, and what the overlap means for each shared goal on that day.

06 / Groups

Beyond pairs

The model is not limited to two people. Per-goal alignment can be computed for yourself, for pairs and for groups: a team, a family, a circle of friends. The same goal lens applies at each level, so a group view shows where a group coheres and where it pulls apart, goal by goal, at a point in time. Days may be ranked for a goal. People never are.

This part is designed and built into the model, and it is not yet calibrated. The next step is a pre-registered forced-choice study that fits the 206 provisional weights to real outcomes. Until then, every number is labelled provisional.

07 / Generation

The model proposes; code checks every claim

The system begins by analyzing the input to determine what it supports. A local model then generates claims one at a time, and code verifies each before the model writes a sentence. After the model writes, code checks again. I review everything before it is released.

I iterated the validator through seven versions from my own reviews, adding checks for truncated claims, unsupported causal leaps, attributing a trait to the wrong person, and claims the inputs do not establish. Every new check is tested before use three ways:

A pilot on the 32B model showed that an over-literal check was rejecting acceptable text. I adjusted both the prompt and the check, which improved plan acceptance from 6 of 31 to 14 of 31. Usable output increased from about 690 to about 1,280 pieces per GPU-hour.

08 / Evaluation

Grading 2.6 million pieces honestly

Grading the 2.6-million-piece library three times over was measured at about 5,600 GPU-hours and was not feasible. I designed a grading strategy that replaces this with statistical lot acceptance sampling using exact binomial plans with stated producer and consumer risk. It adds code checks on every piece and brief-level grading before expansion and includes a plan for a distilled grader.

I set each performance bar before testing and report results as a point estimate and Wilson 95% lower bound. For example, a precision gate passed at 84 of 96 (87.5%). An independent model labels claims in each batch, and its agreement with my verdicts is measured. Those labels then become a regression set for the validator.

09 / Local LLM Stack

A self-hosted inference workstation

I built a self-hosted inference workstation using an RTX 5090 32 GB, Ryzen 9 9950X, and 64 GB RAM to run vLLM in WSL. It serves AWQ and FP8 quantized models through OpenAI-compatible endpoints and can hot-switch between two models with automatic restore.

10 / Agent Organization

A company made of agents

I designed the Skyrule team as a 15-agent AI engineering organization, mirroring a real company with fourteen departments and a Principal Architect. These include the domain practice, relational science, editorial, product design, platform and data engineering, AI and performance engineering, QA and compliance, data science, brand and marketing, legal and trust, finance and operations, program management, the office of the founder, and security and IP protection.

Lanes enforced by tooling, not by instruction

I built a system where code ownership is defined in a machine-readable map and enforced by tooling, so agents cannot change files outside their scope. This turns least privilege from a request into an enforced control.

Decision continuity
I built an append-only log to record founder decisions verbatim. Agents reference this log before asking previously answered questions.
Session continuity
I built a mission file, open-threads register, handoff documents, and coordinator brief to ensure any new agent session could resume without loss.
Code review
I reviewed and integrated 29 pull requests from a cloud engineering agent. Before merging, I ran an isolated checkout with the full test suite and regression controls.
11 / Orchestration

Work that runs while I sleep

I built an autonomous job queue and GPU scheduler in Python that runs on a 15-minute tick. It has separate lanes for CPU, local-model, and cloud-model jobs, and handles priorities, dependencies, start conditions, finish checks, and retry limits. It includes a usage-budget guard and will pause and resume automatically when a model usage limit is reached. Since early October 2026, it has launched 650+ unattended jobs, including overnight GPU extraction runs and parallel multi-agent research batches.

12 / Governance

Quality, security and data protection

Quality governance
I built a register of quality bars, each with proof set before measuring. The quality function can block with a written reason. A weekly review follows, and re-runnable evidence is required for every "done" claim.
Security & IP
I built a dedicated security and IP-protection function into Skyrule with the authority to block any merge or release that weakens a control. A weekly security review is part of the routine.
Privacy by design
Users' personal chart data is never sent to a cloud model and never appears in code, tests, logs or commits; fabricated fixtures only. Consent is the gate for storing anyone else's data
Rights
I maintain rights records and built a quote-permitted gate. The licensed book text remains outside the repository.
Engineering practice
I maintain 1,375 automated tests passing on the integration branch as of October 12, 2026, including known-bad controls that must fail. A release gate blocks any unapproved input changes.
